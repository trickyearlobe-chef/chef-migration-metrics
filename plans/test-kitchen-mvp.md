# Plan: Test Kitchen MVP

## Goal

Validate the Test Kitchen overlay workflow end-to-end against real infrastructure, starting with Proxmox (dev lab), then vSphere, with EC2 as fallback.

## Prerequisites — Encrypted Config Store

The TK MVP depends on the credential injection path working through `config_store`. Complete the encrypted config store work first.

## Specs to Read

- `.claude/specifications/encrypted-config-store.md` — config store (do this first)
- `.claude/specifications/test-kitchen-mvp.md` — MVP scope and targets
- `.claude/specifications/test-kitchen-drivers.md` — driver profiles, credential injection, overlay generation
- `.claude/specifications/node-kitchen-archive.md` — archive format (PARKED but reference for overlay structure)

## Steps

### Phase 1: Encrypted Config Store

See `encrypted-config-store.md` for full spec. Ordered by dependency:

1. Migration `0011_config_store` — create table, migrate `credentials` and `runtime_settings`
2. Datastore CRUD — encrypt/decrypt/get/set/delete/list for `config_store`
3. Credential resolver — update to read from `config_store` instead of `credentials` table
4. Auto-migration — detect full YAML on startup, migrate to DB, write bootstrap file
5. Config reload — pointer swap behind `sync.RWMutex`, re-read from DB each collection run
6. API endpoints — section-specific GET/PUT for each config area
7. Credential API — adapt existing endpoints to use `config_store` backend
8. Admin UI — Organisations page first (most complex), then remaining settings pages
9. Setup wizard — empty `config_store` flow for fresh installs

### Phase 2: Proxmox Validation (Dev Lab)

Requires: Phase 1 complete (credentials stored and injectable via ERB env vars)

1. Store Proxmox and VM transport credentials via Admin → Credentials
2. Configure proxmox driver, platform_map via Admin → Settings or API
3. Generate overlay archive for a representative node
4. Run: overlay → converge → verify → destroy
5. Document any overlay format or gem issues

### Phase 3: Fix Issues from Proxmox Run

- Fix overlay generation bugs surfaced by real converge
- Fix gem dependency or version issues
- Update driver profile defaults if needed

### Phase 4: vSphere Validation

- Apply the same overlay → converge → verify → destroy pattern
- Confirm vcenter driver profile works against the new vSphere environment
- Document any vSphere-specific adjustments

### Phase 5: EC2 Fallback Validation (if needed)

- Only if Proxmox or vSphere are blocked
- Confirm ec2 driver profile works with kitchen-ec2 gem

### Phase 6: Documentation

- Update test-kitchen-mvp spec with findings
- Document validated driver configurations
- Record any environment-specific gotchas in Nuclia KB

## Acceptance Criteria

- All config and secrets managed via DB and admin UI — no YAML editing after first start
- Credential injection into `.kitchen.local.yml` works via ERB env vars (`CMM_TK_SECRET_*`, `CMM_TK_TRANSPORT_*`)
- At least one driver (Proxmox preferred) completes full overlay → converge → verify → destroy cycle
- Overlay archive generated by the app produces a working kitchen project without manual edits
- Known issues and workarounds are documented
- Non-MVP drivers remain in code but are explicitly not validated
